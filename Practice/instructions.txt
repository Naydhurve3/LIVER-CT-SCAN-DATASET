1. FINAL PROJECT GOAL
---------------------

Build a trustworthy, reproducible liver-tumor/lesion segmentation research
pipeline that can:

- prove image-mask spatial correspondence
- train a reproducible canonical baseline
- compare MobileNetV2-U-Net, FAUP-Net, and UWACL-v2 under controlled conditions
- evaluate locked models once on a held-out test set
- produce auditable metrics, figures, manifests, hashes, and reports
- support a later multi-seed research study without misleading claims

The immediate goal is not publication, clinical deployment, or the highest
possible Dice. The immediate goal is to establish trustworthy evidence.

The project is currently single-seed model selection work. Statistical
significance, publication claims, clinical claims, cross-validation, external
validation, dashboards, and manuscript writing remain deferred until the
foundation is valid.

  Evaluate promoted models once on the held-out test set using locked

  If a candidate passes the continuation gate, conduct multiple seeds,
  confidence intervals, ablations, external validation, and publication work.

Dependency rule:

Each objective depends on every objective above it. If Objective 1 is later
invalidated, Objectives 2 through 7 must be reconsidered and any dependent
results must be marked legacy/untrusted.

4. PROJECT STATE MACHINE
------------------------

Every stage must have exactly one current status:

- NOT_STARTED
- READY
- IN_PROGRESS
- PASS
- FAIL_DIAGNOSIS
- BLOCKED_USER
- BLOCKED_EXTERNAL
- INVALIDATED

Status meanings:

NOT_STARTED
  Entry requirements have not been evaluated.

READY
  All entry requirements are confirmed and work may begin.

IN_PROGRESS
  Work is actively being performed and evidence is incomplete.

PASS
  Every mandatory acceptance criterion passed and outputs were preserved.

FAIL_DIAGNOSIS
  The stage produced evidence of failure. The next action is diagnosis, not
  advancing to the next stage.

BLOCKED_USER
  A necessary user decision, manual action, credential, dataset download, or
  hardware run is required.

BLOCKED_EXTERNAL
  A source, service, license, dependency, or hardware condition outside the
  user's and agent's immediate control prevents progress.

INVALIDATED
  New evidence proves that an earlier PASS result is no longer trustworthy.

Allowed transitions:

- NOT_STARTED -> READY
- READY -> IN_PROGRESS
- IN_PROGRESS -> PASS
- IN_PROGRESS -> FAIL_DIAGNOSIS
- IN_PROGRESS -> BLOCKED_USER or BLOCKED_EXTERNAL
- FAIL_DIAGNOSIS -> READY only after a documented fix/hypothesis change
- PASS -> INVALIDATED when upstream evidence changes
- INVALIDATED -> READY only after dependencies are repaired

Never label a stage PASS because code was written, a command exited zero, or a
plot was generated. PASS requires acceptance evidence.

6. HOW TO DETECT FAILURE
------------------------

A process can fail even when there is no exception.

6.1 Hard failure

Examples:

- nonzero command exit
- exception or out-of-memory error
- corrupt file
- missing dependency
- missing checkpoint
- failed assertion/test
- interrupted process without a valid resume artifact

Response:

Capture the exact error, environment, command, input path, and last successful
step. Diagnose before retrying. Do not repeatedly rerun the same command without
changing a hypothesis or condition.


6.2 Silent data failure

Examples:

- matching filenames but anatomically incorrect overlays
- tumor outside liver
- different patients/scans sharing numerical keys
- missing mask treated as empty label
- duplicated slice keys from instance_number wrapping
- split leakage
- different preprocessing applied to checkpoint evaluation

Response:

Stop training/evaluation. Mark downstream results INVALIDATED. Return to the
dataset or provenance stage.


6.3 Silent model failure

Examples:

- predicts all background
- predicts almost every pixel as tumor
- recall is zero or effectively one
- precision near zero
- AUPRC close to or below foreground prevalence
- predicted foreground fraction is implausible
- validation metric spikes once and immediately collapses
- loss decreases while segmentation metrics remain meaningless

Response:

Do not extend epochs automatically. Check threshold, labels, sampler, loss,
output activation, mask values, and tiny-set overfit behavior.


6.4 Silent metric failure

Examples:

- overall Dice dominated by empty slices
- empty masks handled inconsistently
- per-slice and per-volume denominators mixed
- threshold selected on test
- positive-slice Dice mislabeled tumor-only Dice
- surface metrics reported when one surface is empty

Response:

Validate metrics using hand-computed arrays and explicit empty-mask policies.
Mark old reports non-comparable if definitions changed.


6.5 Reproducibility failure

Examples:

- missing config or manifest
- unknown checkpoint preprocessing profile
- missing split hash
- results cannot be reproduced from code commit and dataset version
- dry-run and real run share/overwrite one directory

Response:

Do not treat the result as research evidence. Repair provenance and rerun only
after the artifact contract is complete.


6.6 Research failure

Examples:

- candidate architecture does not improve the locked baseline
- improvement is below the continuation threshold
- result comes from one seed but is described as significant
- test result used to create a new objective/configuration

Response:

Stop architecture expansion. Preserve the negative result. Return to diagnosis
or end the branch. Do not manufacture a new model objective solely to obtain a
positive result.

4. Confirm logits are passed correctly to the loss.

6. Confirm gradients are nonzero and optimizer updates parameters.
7. Try one batch repeatedly with augmentation disabled.
8. Check learning rate and pretrained input-channel adaptation.
9. Compare BCE-only and Dice-only diagnostic losses without redefining the
   canonical objective prematurely.
10. Inspect predicted foreground fraction and probability histograms.

Do not respond to an overfit failure by increasing full-dataset epochs or
switching to FAUP-Net.


12. STAGE 4 - CANONICAL BASELINE THROUGH EPOCH 5
------------------------------------------------

Objective:
Establish a sane, reproducible MobileNetV2-U-Net baseline.

Entry gate:
Stage 3 PASS.

Locked baseline configuration:

- canonical verified dataset
- train volumes 0-103
- validation volumes 104-116
- test locked
- 256x256 grayscale
- no HU transformation for PNG
- no CLAHE
- pretrained MobileNetV2 encoder
- Focal-Dice alpha 0.75, gamma 2.0
- tumor-positive sampler weight 3
- batch size 4
- mixed precision
- DataLoader workers 0
- seed 42
- horizontal flip and intensity shift on training only
- target 5 epochs first
- select best checkpoint on validation positive-volume Dice
- threshold search 0.10 to 0.90 in 0.05 increments on validation only

User/agent responsibility:

- Agent prepares code/config, runs unit/synthetic checks, and provides commands.
- User runs long GPU training manually unless explicitly requesting otherwise.
- User monitors GPU temperature.
- Agent analyzes small JSON/CSV outputs shared after the run.

PASS/sanity gate:

- AUPRC at least 2 times foreground prevalence
- positive-slice Dice greater than 0.10
- precision greater than 0.10
- recall between 0.01 and 0.99
- predicted foreground fraction between 0.25 and 4 times true fraction
- qualitative cases show anatomical tumor prediction, not random regions

Conditional promotion:

Positive-volume Dice should exceed 0.10, or be at least 0.05 with a credible
improving trend over the last three epochs.

Failure interpretations:

All-background prediction:
  Check sampler activation, positive-slice availability, loss scaling,
  threshold, logits, and class imbalance.

Nearly all-foreground prediction:
  Check focal alpha/weights, mask inversion, sigmoid/threshold, sampler excess,
  and target encoding.

Loss decreases but Dice remains near zero:
  Check spatial pairing, empty-dominated loss, metric definition, and threshold.

Recall near one with low precision:
  Overprediction. Diagnose sampler/loss balance and threshold using validation.

High training metric, low validation metric:
  Check overfitting, augmentation mismatch, split distribution, and leakage.

Epoch metric spike then collapse:
  Check checkpoint selection, learning rate instability, small positive-volume
  denominator, and per-volume variance. Do not promote on one unexplained spike.

If gate fails:

Stop. Diagnose dataset, loader, sampler, loss, and label pipeline. Do not run
FAUP-Net or extend to epoch 10 automatically.

16. FAILURE CLASSIFICATION AND PLAYBOOKS
----------------------------------------

Classify every failure before choosing a fix.

TYPE A - Environment

Symptoms:
Import failure, CUDA unavailable, dependency mismatch, temp/cache permission.

Actions:
Inspect environment, versions, PATH, cache location, permissions, and GPU state.
Use the smallest repair. Rerun relevant tests.


TYPE B - Data/provenance

Symptoms:
Missing files, mismatched overlays, invalid geometry, different source content,
duplicate keys, split leakage.

Actions:
Stop downstream work. Capture evidence. Return to Stage 1. Do not patch around
missing provenance in the loader.


TYPE C - Code/test

Symptoms:
Unit/integration failure, wrong tensor shape, checkpoint load error, report
missing fields.

Actions:
Reduce to failing test, fix the implementation, add regression coverage, run
the complete relevant suite.


TYPE D - Optimization

Symptoms:
Tiny-set cannot overfit, unstable loss, zero gradients, NaNs.

Actions:
Use one batch, disable augmentation, inspect gradients, activation/loss contract,
learning rate, target scale, and optimizer state.


TYPE E - Class imbalance/decision threshold

Symptoms:
All background, extreme overprediction, precision/recall collapse.

Actions:
Verify tumor-positive sampler, foreground prevalence, loss parameters,
probability distribution, and validation-only threshold tuning. Change one
controlled element at a time after baseline diagnosis.


TYPE F - Metric/reporting

Symptoms:
Contradictory metrics, empty masks dominate, volume/slice disagreement, missing
provenance.

Actions:
Validate hand arrays, denominators, empty policy, aggregation, and report schema.
Invalidate misleading reports.


TYPE G - Compute/heat/interruption

Symptoms:
GPU temperature too high, Ctrl+C, power loss, out-of-memory.

Actions:
Use graceful checkpoint, cool, resume. For OOM, reduce only approved compute
settings such as batch size after recording the deviation; do not alter model
or data silently.


TYPE H - Research negative result

Symptoms:
Candidate fails continuation gate or provides no credible improvement.

Actions:
Stop that branch, record result, and return to the most plausible limiting
factor. A negative result is valid evidence, not a code failure.


17. HOW TO CREATE, CHANGE, OR RETIRE OBJECTIVES
-----------------------------------------------

The final project goal should remain stable. Stage objectives may change only
when evidence shows the current assumption is false, the objective is already
achieved, or a new blocking dependency is discovered.

Before creating a new objective, document:

- evidence that the current objective is insufficient or invalid
- relationship to the final goal
- exact measurable success criterion
- required inputs and dependencies
- smallest first test
- compute/data/time cost
- what will be stopped or deferred
- fallback if it fails

Good objective example:

"Verify that every canonical tumor mask is contained within its same-source
liver mask and generate a blocking report for exceptions. Success is zero
unexplained outside-liver pixels across 58,638 slices."

Bad objective example:

"Try more models to improve performance."

Objective-change rules:

1. A user request that clearly replaces the current objective takes priority.
2. A user addition should be integrated only if it does not invalidate the
   current stage; otherwise explain the dependency.
3. Major scope changes, destructive actions, external downloads, or new test
   usage require explicit user direction.
4. Do not invent a new objective to hide a failed gate.
5. Do not advance to architecture work while the data objective is unresolved.
6. Retire objectives that no longer affect the final goal and record why.
7. Deferred work must be listed, not silently forgotten.

When evidence changes an earlier assumption:

- state the previous assumption
- show the contradictory evidence
- mark dependent results INVALIDATED
- return to the correct stage
- propose the smallest replacement objective

- split hashes

- model architecture/config

- checkpoint-selection metric
- threshold grid and selected threshold
- environment versions
- Git commit
- start/end/runtime
- best and last checkpoint paths/hashes
- per-epoch history

Run-directory rules:

- never reuse a run directory for a different config
- dry runs use dedicated dry_run directories
- manifests are never overwritten by another run
- resume checkpoint must belong to the intended model/run directory
- interrupted runs save an interrupt checkpoint and status
- --epochs is total target epochs

Legacy checkpoint rule:

Associate every legacy checkpoint with its original simulated-HU or other
preprocessing profile. Never evaluate it silently against the corrected
canonical PNG profile.


21. GIT AND FILE SAFETY
-----------------------

- Inspect Git status before editing.
- Existing/untracked changes belong to the user unless proven otherwise.
- Preserve Practice\next_phase_outputs and other generated user evidence.
- Use targeted patches and commits.
- Do not stage unrelated files.
- Do not commit datasets, checkpoints, caches, or generated result trees.
- Do not use destructive Git commands such as reset --hard.
- Before recursive move/delete, verify absolute paths and obtain user approval.
- Prefer copy/dry-run/manifest-based data reconstruction over in-place mutation.
- Keep current raw dataset folders unchanged until checksums/source registry are
  complete.


22. TESTING POLICY
------------------

Test effort must match risk.

Documentation-only change:
  Validate file content, paths, references, and Git diff.

Small code change:
  Run targeted tests plus related regression tests.

Loader/metric/checkpoint change:
  Run targeted unit tests, synthetic integration, and full suite.

Dataset-build tool:
  Run dry-run fixtures, missing/duplicate/corrupt cases, path-safety checks, and
  deterministic manifest/hash tests before touching full data.

Training lifecycle change:
  Test fresh run, resume, interruption, checkpoint reload, isolated run dirs,
  and manifest transitions.

Before a manual GPU run:
  Unit and synthetic integration tests must pass. A long GPU experiment must
  not be used as a substitute for a failing test.


23. DEFINITION OF DONE
----------------------

Code change done:

- implementation complete
- tests pass
- no unrelated changes
- interfaces documented
- failure exits are meaningful

Stage done:

- every acceptance gate passed
- required outputs saved
- hashes/provenance recorded
- decision documented
- next stage entry conditions satisfied

Experiment done:

- run completed or interruption explicitly recorded
- best/last checkpoints preserved
- validation threshold locked correctly
- evaluation/report artifacts complete
- sanity gate decision recorded

Project sprint done:

- canonical data trusted
- baseline and controlled candidates completed as authorized
- one-time test evaluation performed only after lock
- research continuation decision recorded
- limitations clearly stated

Final research goal done:

- multiple seeds and uncertainty analysis
- appropriate external/robustness validation
- reproducible public/internal artifact package as permitted
- claims supported by evidence and scoped correctly


24. STOP RULES
--------------

Stop and diagnose when:

- spatial alignment is unapproved
- authoritative data is incomplete
- critical tests fail
- tiny-set overfit fails
- baseline sanity gate fails
- provenance is missing
- test data was accessed improperly
- GPU heat is unsafe
- results contradict expected definitions
- a candidate fails continuation criteria

Stop and ask the user when:

- a destructive filesystem action is needed
- a new dataset must be downloaded/licensed
- a major scope/objective change is required
- external credentials or manual GUI steps are required
- user intent cannot be inferred safely

Do not stop merely because work is difficult. Exhaust safe read-only checks and
small tests first.

26. FINAL OPERATING PRINCIPLE
-----------------------------

The project should always answer three questions before spending significant
compute:

1. Are the data and labels unquestionably paired and valid?
2. Is the pipeline proven correct on small deterministic tests?
3. Is the proposed experiment the smallest one that can change the decision?

If the answer to any question is no, create a bounded validation or diagnosis
objective first. Reliable negative evidence is more valuable than an impressive
metric produced by an untrustworthy pipeline.
